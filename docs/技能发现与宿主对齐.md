# 技能发现：与宿主下发给模型的技能目录对齐

> 面向维护者。写于 2026-10-21，对应 CHANGELOG 的「修复：本插件探测到的 skill 数远少于宿主（39 vs 78）」。

## 1. 问题

用户报告：一个空标签的对话里，模型能看到 **78** 条 skill，而本插件的
`POST /skill-tag/api/skills` 只返回 **39** 条。

用户要求：「尽可能地做到 dsh 本身接收到多少 skill，本插件就能探测到多少 skill」。

## 2. 根因：扫盘看不到 provider 贡献的技能

插件原先的列技能路径只用 `scanSkillRoots`：

```js
// lib/index.js（修改前）
mountApi(ctx, services, (cwd) => {
  for (const s of scanSkillRoots(cwd ?? null, config?.customSkillDirs ?? [])) { … }
});
```

而宿主的技能**不都在文件系统根里**。本机实测：

| 来源 | 条数 | 接法 |
|---|---|---|
| `~/.dsh/skills` | 37 | 文件系统根（另有 `kdocs.bak-1.3.1`、`kdocs.bak-2.6.8` 名字含 `.`，被宿主 `SKILL_NAME=/^[a-z0-9]+(?:-[a-z0-9]+)*$/` 丢弃） |
| `~/.agents/skills` | 1 | 文件系统根（`hindsight-coding-agent`） |
| `aegis/skills` | 23 | `applyFilesystemProvider({providerName:"aegis-method-pack", includeDefaultRoots:false, bundledSkillDir})` |
| `mattpocock-skills-dsh/skills` | 25 | 自写 provider（`PACKAGED_SKILL_RANK=550`，其中 14 个 `disable-model-invocation:true`） |
| `@tt-a1i/archify-dsh/skills` | 1 | 同样 insert 一个 `@deepseek-ai/dsh-skill-filesystem` 行 |

并集（目录口径）87 条，按 `disable-model-invocation` 过滤后约 71 条。
扫盘只能覆盖前两行，后三行共 **49 条**是纯 provider 贡献，靠任何文件系统扫描都拿不到。

### 2.1 用户特别点名的两个插件

- **`@tt-a1i/archify-dsh`**：`cordis.patch.yml` 里 insert 一个
  `@deepseek-ai/dsh-skill-filesystem` 行，`id: archify-skill-filesystem`，
  config `{providerName:"archify-plugin", includeDefaultRoots:false,
  bundledSkillDir: <包内 skills/>}`。它不含任何 provider 代码 —— 直接复用宿主
  那个 filesystem provider，只换名字和根目录。提供 1 个 skill。
- **`mattpocock-skills-dsh`**：`cordis.patch.yml` insert `id: mattpocock-skills-dsh`；
  `lib/index.js` 是**自写 provider**（`inject = ["skills"]`），从 `import.meta.url`
  定位 `../skills/<name>/SKILL.md`，`list()` 只读 frontmatter、`get()` 才读 body。
  提供 25 个 skill。

## 3. 宿主的加载机制（asar 0.2.1-rc.2，源码核实）

- `@deepseek-ai/dsh-skill/lib/index.js`：Service 名 `skills`，是**提供者注册表**
  （不是扫描器）。`registerProvider(create)` → `create({signal, invalidate})`；
  `snapshot(options)` → `{skills, complete}`。
- **分层是核心**：

  ```js
  async collectFresh(options) {
    const layers = [this.layers.global, ...this.layers.chainLayers(options.scope)];
    const merged = new Map();
    for (const layer of layers)
      for (const entry of (await this.collectLayer(layer, options)).entries)
        merged.set(entry.candidate.name, entry);   // 近端层直接覆盖
  }
  ```

  同名时**近端层整条覆盖**；同层内按 `rank / providerOrder / localOrder` 排序去重。
- `scope` 是**不透明 key**（`dsh-scope` 的 `scopeOf(ctx)` 读 `ctx[kScope]`），
  宿主把它原样透传给每个 provider 的 `list(options)`。
  **不传 `scope` 就只有 global 层。**
- 模型侧口径（`dsh-tool-skill` 的第二个 `agent/pre-step`，原文）：

  ```js
  const snapshot = ctx.tools.get(skillTool.name, agent) === skillTool
    ? await ctx.skills.snapshot({
        cwd: await ctx.workingDirectory.ensure(agent, signal),
        signal,
        scope: agent,
      })
    : { skills: [], complete: true };
  const skills = snapshot.skills.filter(isModelInvocable);
  ```

  **即「模型看到的技能」= `scope: agent` 的 snapshot 再过滤 `isModelInvocable`。**

## 4. 实现

原则：**以宿主注册表为准，自扫描只作补充**（不取代 —— 设置页没有 agent scope，
宿主 global 快照可能不含 agent 层贡献，自扫描能兜底）。

### 4.1 `createSkillDiscoverer`（`lib/index.js`，已导出）

```js
createSkillDiscoverer({ hostRegistry, rootsScan, agents })
  → async (cwd?, hint?) => Skill[]
```

1. 问宿主 `snapshot({cwd, scope})`；`scope` 由 `hint.conversationId`
   （= sessionId）在 `agents.list()` 里找到的 agent 提供。
2. 自扫描补缺（**只补宿主没有的名字**）。
3. 同名以宿主为准 —— 宿主那份才是模型真正会加载的定义。

### 4.2 `createUpstreamAdapter` 补传 `scope`

原先 `hostRegistry.snapshot({cwd, signal})` 不带 `scope`。现在补上，
并加**嵌套重入保护**：

> 本函数可能被**宿主在收集本插件自己那个 provider 的过程中**调用
> （`provider.list()` → `freshen()` → `summaries()` → `hostRegistry.snapshot()`）。
> 一旦把 `scope` 带上，snapshot 会把 agent 层（也就是我们自己的 provider）
> 重新收集一遍 → 再次 `list()` → 再次 `summaries()` → 无限递归。
> 所以嵌套时直接跳过宿主快照，只用自扫描（fs 扫描无重入）。

#### 4.2.1 两个出口各用一份计数器（2026-10-22 修正）

> 早先的写法是**共用**一份 `snapshotGuard`，理由写的是"这一圈跨两个工厂函数"。
> 那个理由是错的，而且代价很大：共用之后，设置页/UI 快照只要在飞，否认路径就被
> 连坐判成"嵌套" → 跳过宿主快照 → 只看得见扫盘结果 → 包带来的技能全部漏网。
> 详见 `docs/deny-shadow-覆盖率.md`。

递归那一圈其实**只在 adapter 自己内部**：

```
provider.list() → freshen() → recomputeDenials() → upstream.summaries()
  → hostRegistry.snapshot()          ← adapter 自己的守卫在这里 +1
    → 宿主 collect → 收集到本插件自己的 provider
      → provider.list() → freshen()（refreshing 里已有本 sessionId，直接返回）
        → upstream.summaries()       ← 守卫已 > 0，跳过宿主快照 → 收敛
```

`createSkillDiscoverer` 不在这条回路里（它不是 provider，宿主的 snapshot 不会
回调它），所以它的计数器与 deny 路径无关。`apply()` 里现在各自建一份：

```js
const upstreamGuard = { depth: 0 };   // → createUpstreamAdapter
const discoverGuard = { depth: 0 };   // → createSkillDiscoverer
```

另外发现器里做了**同 key 并发合并**（`inFlight`）：设置页一次会并发打好几个
接口，cwd + conversationId 相同的请求共用一次宿主快照，避免"自己把自己判成嵌套"。

即使某次真的降级了（守卫被占 / 宿主抛错），**屏蔽结果也不再受影响** ——
`provider.list()` 会按 `denied` 补齐看不见的名字，见 4.4。

#### 4.2.2 否认路径也要带 `scope`

`recomputeDenials` 算 `universe` 时原来只传 `{cwd}`。agent 层独有的技能
（`@michengai/dsh-skills-manager` / `dsh-skillhub` 的 per-agent provider）
进不了 universe → **永远无法被禁用**。现在 `refreshBySession(sessionId, cwd, scope)`
把 agent 一路传下来。

### 4.3 `src/api.js`：`listSkills` 允许 async

`contextForConfig` / `skillContext` / `resolveSkillPath` / `skillShape` /
`convPayload` 全部 await 化；新增第三参 `hint = {conversationId, workspaceId}`
透传给发现器。

### 4.4 deny-shadow 按**名字**发射，不按"这一趟看得见谁"

`createFilterProvider.list()` 原来只遍历 `upstream.summaries()` 的结果：

```js
for (const summary of summaries) if (denied.has(summary.name)) shadows.push(...)
```

于是**发射范围 = 本次能看到的 summary**。任何一次"看不见"的降级（守卫被占、
宿主快照抛错）都会让 `denied` 里那些包带来的技能一条影子都收不到 —— 它们是原样
透给模型，而不是被屏蔽。这就是 aegis / mattpocock / archify / office /
tagging-skills 那 17 个长期漏网的原因（详见 `deny-shadow-覆盖率.md`）。

现在分两段：

1. 看得见的：照抄上游 summary（保留 `path` / `description`），只换 `invocation`
   与 `provider`，`rank` 取 `0`；
2. 看不见的：给 `denied` 里的每个名字**造一条最小合法候选** —— 屏蔽是按键名
   生效的，不需要知道它长什么样。

`rank: 0` 是硬约束：宿主只在**层内**按 `rank` 升序去重（`compareIndexedCandidates`），
跨层是"近层整条覆盖"。照抄上游 rank（office = `BUNDLED_SKILL_RANK` 600）时，
同层里若有 rank 更小的同名候选，影子会被顶掉。

`denied` 里的历史脏名字（带空格 / 大写 / 中文）必须先过宿主的 kebab-case 校验
再发 —— 一个不合法候选会让**整个** `provider.list()` 抛错，宿主随即丢弃本插件的
全部贡献（日志 `skill provider "skill-tag" skipped`），比漏一个更糟。

## 5. 约束（踩过的坑）

- **cordis 服务必须声明式注入**：`export const inject` 里没有的服务，读 `ctx.xxx`
  会**直接抛** `cannot get property "xxx" without inject`。只能 `ctx.get(name)` + try/catch。
- **注册给宿主的回调里抛异常 = host fatal**（2026-10-20 崩过两次）。
  `domain/changed` 监听器、provider 的 `list`/`get`、`apply()` 同步栈，全部 self-contain。
- `lib/client.js` no-cache，刷新即生效；`lib/index.js` / `src/*` 是 ESM，**必须重启桌面进程**。
- 若你按「本地开发」方式装（源码放 A 处、profile 的 `node_modules` 里放一份 B），
  两处是**不同物理文件**，改完必须手动复制并校验哈希。

## 8. 刷新技能列表 / 失效关联（2026-10-31）

### 8.1 症状

把 `mattpocock-skills-dsh` 插件 disable 之后，技能确实从模型视野里消失了，
但本插件的界面**仍然认为它们在**，数字也不降。

### 8.2 为什么没自动刷新

两层原因，都不是"缓存没清"：

1. **服务端本来就是实时的**。`GET /skills` 每次都重新问宿主 `ctx.skills.snapshot()`
   + 补一次自扫描，没有任何缓存层。连问两次结果完全一致。
2. **前端把"幽灵技能"也算进了计数**。`skillLinks` 表里存的是**历史关联记录**，
   技能消失后这些记录不会自己消失（这是对的：插件只是被临时关闭，不该丢掉
   用户手工打的标签）。旧实现在 `SkillTagPage` 里把它们并进 `names`：

```js
// 旧实现：先扫描结果，再补"只存在连接记录"的幽灵
for (const l of links) if (!seen.has(l.skillId)) names.push({ name: l.skillId, ghost: true });
// …然后 `技能 (${names.length})` ← 幽灵也被数进去了
```

本机实测：真实 82 个 + 幽灵 25 个（全部来自被 disable 的 mattpocock 插件）=
界面显示 **107**。所以"刷新按钮"必须同时解决**计数口径**，否则点了数字还是不变。

### 8.3 改动

| 位置 | 改动 |
| --- | --- |
| `src/api.js` `GET /skills` | 额外返回 `stale: [{skillId, tagIds}]` —— 有标签关联但这次发现不到的技能。**只报告，不删**。 |
| `src/api.js` `POST /skills/purge-stale` | 只删这些失效关联。发现结果为 **0 时直接 409 拒绝**（`NO_SKILLS`），避免宿主未就绪时把全部关联当成失效。支持 `skillIds` 白名单只删勾选的。 |
| `lib/client.js` `Section` | 新增 state `stale`；新增 `refreshSkills()`（重新拉 `/state` + `/skills`）与 `purgeStale()`（二次确认后调 purge）。 |
| `lib/client.js` 主页面 | 导航栏加「刷新技能列表」；有 stale 时顶部橙色提示条 + 「清理失效关联」。 |
| `lib/client.js` `SkillTagPage` | **计数只算真实技能**：`技能 (N)` + `· 失效 M`；失效项在左列下方单列（带删除线、不显示 📁）；选中失效技能时给解释条。 |

### 8.4 为什么不自动删

关联是用户手工打的标签。插件被临时关闭 ≠ 用户放弃这些标签 —— 重新启用后
应该恢复。所以：**默认只标记，删除必须显式点击**，且点击时列出前 8 个名字
并说明"重新启用插件后需要重新打标签"。

### 8.5 验收

```
1. 关掉贡献技能的插件 → 点「刷新技能列表」
   → 「技能 (N)」降到真实值；橙色条显示「有 25 个技能仍有标签关联，但当前发现不到」
2. 重新打开插件 → 再点刷新
   → 数字回升，橙色条消失，之前的标签关联**原样恢复**（因为一条都没删）
3. 点「清理失效关联」→ 二次确认 → 关联被删，橙色条消失
   → 再打开插件时这些技能不再带标签（预期行为，有文案提示）
```

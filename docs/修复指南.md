# 修复指南：标签打对了，会话里却没有那个技能

> 面向维护者。写于 2026-11-02，对应 CHANGELOG 尚未收录的一次线上排查（v0.1.13）。
> 适用场景：**用户在某个会话上打了标签、或给某个工作区配了标签，但模型侧技能目录里
> 根本没有那些名字**。本文给出判定树、逐项取证命令、以及三种可比选的修法。

## 1. 先分清三种"没有"

同样是"看不见"，根因完全不同。**在动手之前必须先定位到哪一层断的**，
否则会去修一个没坏的地方（0.1.13 之后最常踩的坑）。

| 层 | 断了的典型表现 | 判定依据 |
| --- | --- | --- |
| **A. 发现层**（技能根本没被扫到） | 该技能不在会话的技能目录里，且也不在 `/skill-tag/api/skills` 里 | 该技能的任何标签规则都不可能命中 |
| **B. 匹配层**（扫到了，但被 deny） | 在 `/skills` 里出现，描述被加上 `[blocked by skill-tag]` | 标签条件没覆盖它，或被 `disabledSkills` 点了 |
| **C. 生效层**（匹配了，标签压根没写进去） | `skill_tag.json` 里对话 `own.config` 不含那个标签 | 用户打到了工作区，但对话是冻结快照 |

历史上 0.1.x 修过的 bug 几乎全在 B（`deny-shadow-覆盖率.md`）和"对话冻结"（`对话管理标签.md` §继承）。
**A 这一层几乎没有文档**，而它恰恰是"我打了标签为什么没反应"最常见的答案。

## 2. 判定树

```
模型侧技能目录里没有技能 X
├─ X 在 GET /skill-tag/api/skills 里吗？
│   ├─ 不在 → A 发现层。可能：该会话的预设/插件根本没扫描 X 所在目录
│   └─ 在  → 继续
│       ├─ X 的 description 以 "[blocked by skill-tag]" 开头吗？
│       │   ├─ 是 → B 匹配层。看 effective.config 是否覆盖 X，看 disabledSkills
│       │   └─ 否 → C 生效层。看该会话 own 是否真的写了标签
```

## 3. 取证命令（只读，按顺序打）

端口每台机器不同，**不要猜**：用运行时上下文里的 Web GUI URL，或
`Get-NetTCPConnection -State Listen | Where OwningProcess -eq <dsh pid>`。

```powershell
$b = "http://127.0.0.1:<PORT>/skill-tag/api"
$cid = "session-xxxxxxxx-..."     # 用户报的那个会话 id

# ① 全域技能表（不带 hint）：本插件认为自己"能看见"的全部技能
curl.exe -s "$b/skills"                              > $env:TEMP\sk-all.json
# ② 带会话 hint：等同该会话代理看到的集合
curl.exe -s "$b/skills?conversationId=$cid"          > $env:TEMP\sk-conv.json
# ③ 该会话的生效配置 + view + catalog
curl.exe -s "$b/conversations/config?conversationId=$cid" > $env:TEMP\cfg.json
# ④ 最终候选（走对话四区口径）
curl.exe -s "$b/conversations/candidates?conversationId=$cid"
```

读 ① / ② 里的 `description` 前缀判 B 层；读 ③ 的 `config.orTags` 判 C 层；
**① 和 ② 里都没有该名字**就是 A 层。

### 3.1 模型侧到底看到了什么（唯一权威口供）

`~/.dsh/storages/skill_tag.json` 和 `/conversations/config` 都是**本插件的口径**，
可能和模型真实收到的不一致（见 §6.1 的假阳性）。真正的口供在会话 transcript 里：

```powershell
$f = "$env:USERPROFILE\.dsh\sessions\<编码后的cwd>\<sessionId>\session.v4.jsonl.zstd"
$out = "$env:TEMP\sess.jsonl"
node -e "const z=require('zlib'),fs=require('fs');
  const b=fs.readFileSync(process.argv[1]);
  const magic=Buffer.from([0x28,0xB5,0x2F,0xFD]); let idx=[],p=0;
  while((p=b.indexOf(magic,p))!==-1){idx.push(p);p+=4;}
  const parts=[]; for(let k=0;k<idx.length;k++){
    const s=idx[k], e=(k+1<idx.length?idx[k+1]:b.length);
    try{parts.push(z.zstdDecompressSync(b.subarray(s,e)).toString('utf8'))}catch{}
  } fs.writeFileSync(process.argv[2], parts.join(''));" $f $out
```

然后 grep `<available_skills>`。那一条 user 消息就是模型收到的**完整技能目录** ——
比对它的名字列表与 `/skills` 的差集，就能立刻分清"插件以为可见"和"模型真的可见"。

> transcript 是**分帧 zstd**（一条消息一帧），整文件 `zstdDecompressSync` 只会解出第一帧
> （通常只有 219 字节的 `{"type":"session"...}` header）。必须按 magic 逐帧解压，见上面的脚本。

同一条 transcript 里还有 `agent-preset/selected` 事件，能看出该会话用的是哪个预设 ——
A 层问题九成出在这里。

## 4. A 层：发现层（最常见，也最容易被误判成插件 bug）

### 4.1 根因：预设可以整体关闭默认技能根

`@deepseek-ai/dsh-skill-filesystem` 的默认根（详见运行时文档 "Roots and priority"）：

| Rank | Source | Path |
| --- | --- | --- |
| 100 | `project-dsh` | `<projectRoot>/.dsh/skills` |
| 200 | `project-agents` | `<projectRoot>/.agents/skills` |
| 300 | `custom` | `Config.customSkillDirs` |
| 400 | `user-dsh` | `<dshHome>/skills` |
| 500 | `user-agents` | `<agentsHome>/skills` |

`includeDefaultRoots: false` 会把 100/200/400/500 **整排删掉**，只剩 `customSkillDirs`。

于是任何写了这行的预设（本机实测：StudyMate 的「学习模式」、`@tt-a1i/archify-dsh` 的隔离根）
都把 `~/.dsh/skills` 挡在门外。用户在那类会话上打 `来自:dsh-home` 之类的标签，
**规则算得再对也没有对象可匹配** —— 因为早在发现阶段就没了。

取证：

```powershell
# 1) 找该会话用的预设
Select-String -Path "$env:USERPROFILE\.dsh\sessions\...\session.v4.jsonl" -Pattern "agent-preset/selected"
# 2) 看那个预设有没有关默认根
Select-String -Path "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\<pkg>\preset\**\agent.cordis.yml" -Pattern "includeDefaultRoots"
```

### 4.2 三种修法

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A1** 全局放开 | 在 profile 的 `cordis.patch.yml` insert 一条独立 `dsh-skill-filesystem`（`providerName` 唯一、`includeDefaultRoots: true`） | 所有预设都吃到 `~/.dsh/skills`，预设原本的隔离设计被削弱 |
| **A2** 追加额外根 | 在**该预设**的 `customSkillDirs` 末尾追加一个独立目录 | 改的是包目录，`pnpm update` 会覆盖 |
| **A3** 换预设 | 让用户在该会话切到不隔离的预设 | 隔离带来的专属技能随之消失，可能整条流程跑不动 |

**推荐 A2**，并且把"额外根"做成**用户自己的目录 + junction**，而不是往别人包里塞文件：

```powershell
# 1) 建一个自己的额外技能根，用 junction 指回真实技能（升级自动跟随，不会两份内容打架）
$extra = "$env:USERPROFILE\.dsh\studymate-extra-skills"
New-Item -ItemType Directory -Force -Path $extra | Out-Null
foreach ($n in @('obsidian-markdown','obsidian-bases','obsidian-cli','json-canvas','defuddle','knap')) {
  cmd /c mklink /J "$extra\$n" "$env:USERPROFILE\.dsh\skills\$n" | Out-Null
}
```

```yaml
# 2) 在目标预设的 skill-filesystem 行追加一条（保留原有占位符那行）
- id: skill-filesystem
  name: '@deepseek-ai/dsh-skill-filesystem'
  config:
    includeDefaultRoots: false
    customSkillDirs:
      - '__STUDYMATE_SKILLS__'
      - 'C:\Users\ThinkPad\.dsh\studymate-extra-skills'   # 本地追加（非官方）
```

要点：

- **路径用反斜杠**。YAML 单引号里 `\` 不转义，写正斜杠在 Windows 上也能被 Node 接受，
  但和包内既有写法保持一致更省排查成本。
- **预设是启动时装配的**，改完必须**重启桌面进程**（不是刷新页面）。
- 改的是 `node_modules` 里的文件：`pnpm update <pkg>` 会把它整个换掉，那行会消失。
  **升级后必须复查**（见 §7 回归清单）。备份文件名建议带时间戳：
  `agent.cordis.yml.bak-before-extra-skills-<ISO>`。

> 为什么 native 加载不会被启动流程覆盖：`bin/studymate.mjs` 的 `installPayload`
> 把 `preset/<id>` 拷到临时目录后**在副本上**替换 `__STUDYMATE_SKILLS__`，
> 包目录本身是只读材料（源码注释明确写了"原生加载也不写包目录"）。
> 但它读的是包目录里的**当前内容**，所以手工改动会带进下次启动 —— 这点是好事，
> 也是 A2 可行的前提。

## 5. B 层：匹配层（0.1.x 已修过多轮，改动前先读旧文档）

先读 `deny-shadow-覆盖率.md` 与 `技能发现与宿主对齐.md`。这里只列**判据**：

- 运行时拒绝集 = `computeRuntimeDeniedSkillIds(effective, {universe, candidates, linkedSkillIds})`（`lib/index.js`）；
- `effective` 只来自 **own**，永不回退工作区实时配置（2026-10-31 定的口径，见 `recomputeDenials` 注释）；
- `own === null` = 从未配置 = 空条件 = 掌握全部技能。

改这块之前先确认：**别把"own 为 null = 全部"这条改掉**。它是"看一眼就被冻结"那类老 bug 的解药。

## 6. 已知缺陷

> 0.1.14 修掉的是另一类错位：「界面按标签算命中、模型按 invocation 算下发」，
> 现在右列标题会同时给出两个数，见 CHANGELOG 0.1.14。
> 0.1.15 修掉了下面 6.1（issue #1），本条保留作历史缺陷记录；6.2 仍未修。

### 6.1 对话面板假阳性：没有活跃 agent 时退回全局技能表（**0.1.15 已修**）

`src/api.js` 的 `contextForConfig` 只把 `{conversationId}` 当 hint 传给
`createSkillDiscoverer`，而后者在 `agentFor(conversationId)` 返回 null 时**直接退化成
不带 `scope` 的宿主快照**（`lib/index.js` 的 `snapshotSkills`）：

```js
const scope = agentFor(hint?.conversationId);
const snap = await hostRegistry.snapshot({ ...(cwd ? { cwd } : {}), ...(scope ? { scope } : {}) });
```

后果：会话没有在跑时打开「对话 → 管理标签」，面板展示的是**全局技能表**
（例如 128 条，含 14 条标签命中），而该会话真实只有 10 条。用户看到"面板里明明有、
模型里明明没有"，就是这个错位。

修法（0.1.15 已实施）：`agentFor` 查不到 agent 时不再静默去掉 `scope`，而是把这一趟
快照标记成**视角不完整**（发现器数组上的 `VIEW_COMPLETE` Symbol + 逐条 `registered: null`），
界面把那一批标成「暂不可判定」并给对话入口加一句「该会话未运行，以下为全局视角」，
「模型可见 N」也不再把它们算进去。判据与取舍见 CHANGELOG 0.1.15。

### 6.2 `/workspaces/skills` 与 `/conversations/skills` 不存在

客户端 `manageScope()` 会拼出 `skillsPrefix = "/conversations/skills"`，
但服务端只有 `/conversations/skills/{add,remove,disable,enable}`。
拿到裸前缀会 404（`{"ok":false,"error":"not found: /conversations/skills"}`）。
这是良性的（客户端不请求裸前缀），但排查时容易被误导 —— 用它做健康检查会误判成插件没起来。

## 7. 升级 / 重启后的回归清单

`dsh-skill-tag` 或任何"提供技能根"的插件升级之后，按这个顺序跑一遍（5 分钟）：

1. `GET /skill-tag/api/skills` 条数与升级前对比，突变超过 ±10 就该查。
2. 目标会话的 `GET /conversations/config?conversationId=...` —
   `expression` 是否还在、`expressionIssue.ok` 是否为 true（`false` = 引用了已删除/改名的标签）。
3. 自建额外技能根是否还在：`Test-Path ~/.dsh/studymate-extra-skills`，
   以及目标预设的 `customSkillDirs` 里那行是否被 update 冲掉。
4. 拉一次目标会话 transcript，确认 `<available_skills>` 里有该有的名字（§3.1 脚本）。
5. 重启桌面进程后重复 1-4（预设装配发生在启动时，不重启看不到变化）。

## 8. 一句话总结

> 标签只决定"匹配"，**不决定"发现"**。
> 打上标签仍然看不见，先问：这个会话的技能根里，到底有没有这个技能。

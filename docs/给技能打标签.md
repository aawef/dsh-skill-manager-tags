# 给技能打标签（可移植指南）

> 面向：**装了 dsh-skill-tag 插件的任意一台机器上的 agent**。
> 当你（或你的用户）说「给技能打标签 / 整理一下这些 skill / 给它们分类」时，按本文档做。
>
> **最重要的一条**：本文档里出现的任何具体标签名（`aegis`、`mattpocock-skills-dsh`、
> `office-skills`…）都只是**某一台机器上的实例**，不要照抄到你自己的机器上。
> 你要做的是用这里的**推导法**，在你自己机器上的技能清单里生成属于它的标签体系。

---

## 0. 这份文档解决什么问题

标签的作用：让「工作区 / 对话」用一条布尔表达式（语法见
[标签组配置.md](./标签组配置.md)，`+`=OR、`*`=AND、`*` 优先、可加括号）
从几十上百个技能里**选出一个子集**下发给模型。

所以打标签不是给技能做分类学，而是为了让**表达式能写出用户想要的那句话**：

| 用户想说的话 | 表达式 |
|---|---|
| 只要某个包带来的技能 | `<包名> * plugin` |
| 只要我自己装的技能 | `dsh-home + agents-home` |
| 某个领域全部（含别的包里的同类） | `pdf` |
| 只要那个路由器本身，不要它路由到的簇 | `router * routes:office` |

标签体系因此设计成**三根轴**（互不排斥，同一个技能可以同时挂三轴的标签）：

1. **来源轴** —— 这技能是哪来的（哪个包 / 哪个技能根目录）。**可自动推导**。
2. **领域轴** —— 它是干什么的（pdf / git / testing …）。**要读 description 判断**。
3. **路由轴** —— 簇标签 + `router` 旋塞，用来圈住「一个路由器和它路由到的技能」。

---

## 1. 先拿到本机的技能清单

插件在宿主的 Web server 上挂了一套 HTTP API，前缀固定：

```
<DSH Web GUI 的 origin>/skill-tag/api
```

GUI 端口每台机器不一样（本机写文档时是 `11347`）。**不要猜端口**：

- 你的运行时上下文里就写着 DSH Web GUI 的 URL（形如 `http://127.0.0.1:NNNNN`）——用它；
- 拿不到就 `netstat -ano -p tcp | grep LISTENING` 找 dsh 桌面进程的那个端口；
- 或看 `~/.dsh/profiles/<profile>/hub.log` 里最近的启动记录。

```bash
curl -s "http://127.0.0.1:<PORT>/skill-tag/api/skills" | head -c 800
```

返回（`GET` 与 `POST` 等价，参数既能放 query 也能放 body）：

```json
{ "ok": true, "skills": [
  { "name": "pdf", "description": "…", "path": "C:\\...\\SKILL.md", "source": "C:\\...\\.dsh\\skills" }
] }
```

- `name` —— 链接的键，也是表达式最终选中的东西。
- `description` —— **领域轴唯一的判断依据**，一定要读。
- `path` —— SKILL.md 绝对路径；**`null` 表示内置/来自 provider，文件系统上不可见**。
- `source` —— 文件系统根（扫盘来的技能）或 `bundled` / `custom`（provider 贡献的）。
  注意 `source` 是 `bundled` 的技能可能来自**好几个不同的物理位置**，只能靠 `path` 区分。

如果技能数明显少于你在 `/skills` 页面看到的数，加 `cwd` 再试一次（项目级
`.dsh/skills` 只有在传了 cwd 时才扫得到）：

```bash
curl -s -X POST "http://127.0.0.1:<PORT>/skill-tag/api/skills" -H 'content-type: application/json' \
  -d '{"cwd":"D:/work/repo"}'
```

## 2. 来源轴：按「技能在哪」自动推导

**不要手写名单。** 规则只有四条，按 `path` 从上往下匹配（实现见
`src/domain/origin.js`，可直接 `import { originTagOf }`）：

| 条件 | 来源标签 | 例子 |
|---|---|---|
| `path` 含 `/node_modules/<pkg>/` | 包名（`@scope/name` 保留 scope） | `aegis`、`mattpocock-skills-dsh`、`@tt-a1i/archify-dsh` |
| `path` 含 `/resources/runtime/<dir>/` | 那个目录名 | `office-skills` |
| `path` 为 `null`，或含 `.asar` | `builtin` | 桌面端内置技能 |
| 其余（文件系统根扫到的） | 看 `source` 根：`<home>/.dsh/skills` → `dsh-home`；`<home>/.agents/skills` → `agents-home`；项目级同名根 → `project-skills` / `project-agents`；自定义根 → 根目录最后一段 | `dsh-home` |

**再挂一个 `plugin` 旋塞**：凡是「某个包 / 运行时送进来的」（即非
`dsh-home`/`agents-home`/`project-skills`/`project-agents`）的技能，额外共挂 `plugin`。

为什么值得多挂这一个：

- `<包名> * plugin` = 「只要这个包带来的技能」——用户最常说的话；
- `<包名>` 单用也一样（来源标签只挂这一个包），但有了 `plugin` 就能写
  `plugin`（所有包带来的）、`dsh-home + agents-home`（所有我自己装的）这种跨包表达；
- 它让「包带来的」和「我自己放的」在表达式里可区分，这是过滤的主要维度。

**`builtin` 的处理**：path 不可见时无法推导，全部落 `builtin`。如果这堆技能名字有
明显公共前缀（`office` / `office-docx` / `office-pptx` …），**手工补一个来源标签**
（如 `office-skills`），别让它们糊成一团。这是唯一需要你动脑的来源轴步骤。

## 3. 领域轴：读 description 归类

没有自动推导，只能读。但有几个纪律能让结果可用：

- **先聚类再命名**：把 96 条 description 通读一遍，按语义堆成若干堆，
  再给每堆起一个 kebab-case 小写名。**不要**先想好标签名再往里塞。
- **一个领域标签至少挂 2 个技能**。只挂 1 个的标签等于给这个技能起了个别名，
  直接用技能名更清楚——除非它是路由轴用的簇标签（见 §4）。
- **跨包归类才有价值**：`pdf`、`pdf-translator`、`translate-pdf` 可能来自三个不同的
  包，但都挂 `pdf`，于是「我要所有 pdf 相关」一句话就够。这正是领域轴存在的理由。
- **数量控制在 10~25 个**。太少选不出子集，太多维护不动。
- 下面是**候选词表**（不是清单，按你机器上实际有的技能裁剪）：
  `code-review pdf docx xlsx pptx diagram cli-anything planning testing debugging git
  memory doc-writing web dsh-ops mcp visual-design interview architecture
  agent-workflow teaching`
- 已有的旧标签要保留：先 `GET /skill-tag/api/state` 看现存 `tags` 和 `skillLinks`，
  已有的链接不要无谓重写。

## 4. 路由轴：簇标签 + `router` 旋塞

有些技能干的事是「帮你挑别的技能」——description 里会出现这类措辞：

> Use when users request … Use when the user asks to … **Router over the skills** …
> Load to choose the relevant workflow. Ask which skill or flow fits your situation.

把它们标成**路由器**，然后：

- 路由器本身挂 `router`；
- 路由器 **+ 它路由到的那一整簇** 一起挂 `routes:<路由器名>`。

两条表达式于是可以做两件不同的事：

| 表达式 | 含义 |
|---|---|
| `routes:office` | 整个簇（路由器 + 7 个 office 技能） |
| `router * routes:office` | 只要那个路由器本身（4 个 router 里的 office 那个） |

这比「再造一类关系标签」更省：一个旋塞 `router` 就能把「整簇」和「只要路由器」
分开，不必为每个簇造第二个标签。

## 5. 落地：API 调用序列（按这个顺序）

所有路由都接受 GET 与 POST，参数用 `q(k) = body[k] ?? searchParams.get(k)` 取值，
所以 GET 也能带参。**除 `/tags/rename` 等少数写操作外不必纠结方法。**

### 5.0 先读现状

```bash
curl -s "http://127.0.0.1:<PORT>/skill-tag/api/state"
# → { ok, tags:[{tagId,name,createdAt}], skillLinks:[{skillId,tagIds}], templates, workspaces, conversations }
```

### 5.1 建标签

```bash
curl -s -X POST ".../tags" -H 'content-type: application/json' \
  -d '{"tagId":"t-lz3k1","name":"pdf"}'
# → { ok:true, tag:{tagId,name,createdAt} }
```

- `tagId` 自己生成，形如 `t-` + `Date.now().toString(36)`（客户端就是这样生成的）。
- **同名会报** `tag name 'pdf' already exists`（`src/service.js`）。这不是 bug，
  是幂等信号：先读 `/state` 里已有的 `tags`，已存在就复用它的 `tagId`。

### 5.2 打链接 —— ⚠️ 整体覆盖，必须先读再合并

```bash
# 读：拿到这个技能现有的全部 tagIds
curl -s ".../skills/tags?skillName=pdf"
# → { ok, skillName, tagIds:[...], skill:{...}, tags:[...] }

# 写：把「旧的 ∪ 新的」整个传回去
curl -s -X POST ".../skills/tags" -H 'content-type: application/json' \
  -d '{"skillName":"pdf","tagIds":["t-a","t-b","t-c"]}'
```

**这是最容易踩的坑**：`/skills/tags` 的写是**整体覆盖**，传什么就是什么。
只传新标签会把旧标签清掉；`tagIds: []` 等于清空该技能的全部关联。
所以每次写之前先读回旧的再合并（幂等脚本就靠这一点做到可重跑）。

### 5.3 校验表达式，再存进工作区

```bash
# 先验证（不落盘），顺便看 DNF 展开
curl -s -X POST ".../templates/validate" -H 'content-type: application/json' -d '{"expression":"aegis*plugin"}'
# → { ok, errors, warnings, normalized, tagIds, dnf, config }

# 存进工作区条件
curl -s -X POST ".../workspaces/expression" -H 'content-type: application/json' \
  -d '{"workspaceId":"9b82dcc5-…","expression":"aegis * plugin"}'
# → { ok, workspace:{config,expression,manualSkills,disabledSkills}, validation }

# 看它到底选中了哪些技能
curl -s -X POST ".../workspaces/skills" -H 'content-type: application/json' -d '{"workspaceId":"9b82dcc5-…"}'
# → { ok, candidates:["brainstorming", ...], universe:[...], catalog:[...] }
```

**`candidates` 的数量必须和你预期一致**，否则是标签打漏了或表达式写错了。
这一条是整件事唯一真正的验收标准。

### 5.4 常用表达式存成模板（可选）

```bash
curl -s -X POST ".../templates" -H 'content-type: application/json' \
  -d '{"templateId":"tpl-lz3k2","name":"office 全家","expression":"routes:office"}'
```

`/templates/evaluate` 与 `/templates/expand` **要 `templateId` 而不是 expression**
（传 expression 会报 `template 'null' not found`）。

### 5.5 路由清单

| 路径 | 用途 |
|---|---|
| `/skills` | 本机技能清单（可带 `cwd` / `conversationId` / `workspaceId`） |
| `/skills/tags` | 一个技能的标签（读/整体覆盖写） |
| `/skills/reveal` | 打开技能所在文件夹 |
| `/state` | 全量快照（tags / skillLinks / templates / workspaces / conversations） |
| `/tags` `/tags/rename` `/tags/link` `/tags/unlink` `/tags/delete` | 标签增删改；`delete` 返回 `affectedWorkspaces` |
| `/workspaces/{ensure,expression,skills,skills/add,skills/remove,skills/disable,skills/enable,apply-template,sync-all}` | 工作区条件与右列 |
| `/conversations/{ensure,config,inherit,expression,candidates,…}` | 对话级覆盖（同形） |
| `/templates/{validate,evaluate,expand}` `/templates` `/templates/update` `/templates/delete` | 模板 |

## 6. 一键脚本：`tools/auto-tag.mjs`

来源轴是纯推导，交给脚本；领域轴要判断，脚本只能给建议。

```bash
# 默认 dry-run：只打印「每个技能会被打上什么」，不写任何东西
node tools/auto-tag.mjs http://127.0.0.1:<PORT>

# 只落地来源轴（含 plugin 旋塞），不动领域轴
node tools/auto-tag.mjs http://127.0.0.1:<PORT> --apply

# 领域轴：用关键词启发式给建议（务必人工复核后再写）
node tools/auto-tag.mjs http://127.0.0.1:<PORT> --domain hints

# 领域轴：用你自己写的映射文件
node tools/auto-tag.mjs http://127.0.0.1:<PORT> --domain ./my-domain-map.json --apply
```

它做的事：

1. `GET /skills` 拉清单 → `src/domain/origin.js` 推导来源标签（+ `plugin`）；
2. 领域标签来自 `--domain hints`（`tools/domain-hints.mjs` 的关键词表，
   只是**起点建议**）或 `--domain <file>`（形如 `{"pdf":["pdf","translate-pdf"]}`）；
3. `GET /state` 复用已存在的同名标签（同名创建会报错，所以这一步是必须的）；
4. 每个技能 `GET /skills/tags` 读回旧 tagIds，合并后再 `POST` 覆盖写 —— 因此**幂等**，
   反复跑不会丢标签也不会重复；
5. 打印汇总：`tagsCreated` / `linksWritten` / `unknownNames`（映射文件里写了不存在的
   技能名会列在这里）/ `builtinClusters`（建议手工补来源标签的那堆）。

`--domain <file>` 的映射文件建议按你机器上真实 description 写，写完后**重跑一次**
确认 `unknownNames: []`、`tagsCreated: 0`（第二次跑不再新建任何东西 = 幂等）。

## 7. 常见错误

| 现象 | 原因 |
|---|---|
| `tag name 'X' already exists` | 同名重复创建。先读 `/state` 复用已有 tagId |
| 打完标签发现旧标签没了 | `/skills/tags` 是整体覆盖，没先读回旧 tagIds |
| `template 'null' not found` | `/templates/evaluate`、`/templates/expand` 要 `templateId`，不是 expression |
| 表达式报错 / 选中集合不对 | 标签名含空格或 `+ * ( )` 引号 → 表达式里必须加引号。来源标签已用 `safeTagName` 把这些字符换成 `-`；起名时照做 |
| 技能数偏少 | 没传 `cwd`，项目级 `.dsh/skills` 没扫进来 |
| `candidates` 数量不对 | 标签打漏了 / 表达式写错。**以此为准，不要以「看起来差不多」为准** |

## 8. 交付检查清单

- [ ] `/state` 里 `tags` 数量合理（不是 3 个也不是 200 个）；
- [ ] 来源轴覆盖全部技能（含 `builtin` 那堆已手工补标签）；
- [ ] 每个领域标签 ≥2 个技能；
- [ ] 路由器挂了 `router`，簇挂了 `routes:<名>`；
- [ ] 至少用一条表达式跑过 `POST /workspaces/skills`，`candidates` 数量与预期一致；
- [ ] 脚本重跑一次是干净的（`tagsCreated: 0`、`unknownNames: []`）。
